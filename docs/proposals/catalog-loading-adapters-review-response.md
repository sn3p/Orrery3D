# Response: catalog loading proposal review

**13 September 2026.** Addressed the supplied [review](catalog-loading-adapters-review.md) in [proposal revision 2](catalog-loading-adapters.md). The original review is unchanged. This response records design dispositions, not implemented runtime fixes or permission to deploy.

The simplification direction is sound. The revised proposal uses one source class, one committed prefix, fixed lookahead, fixed buffers and measured main-thread preparation. Several suggested deletions would remove required shared-contract behavior or overstate earlier evidence; those are qualified below.

| Finding | Disposition | Change or reason |

| 1. A/B already decided | **Partly accepted** | Remove a separate whole-file implementation/module hierarchy; retain a small whole mode using the same validated file reader. Earlier measurements had no equivalent runtime index/file verification and used older DPR/settings. They establish risk, not a controlled result for the revised loader. Both modes and comparable verification remain in the approved relay. |
| 2. Provisioning first | **Accepted with corrected scope/order** | Make local provisioning and deployable assembly stage 1; stage outside `dist`, build with `--output-clean`, then copy/verify. | 4. Pages short-visit bandwidth | **Accepted** | Add soft-bandwidth arithmetic and short-visit bytes to decision criteria. About 2,900 full downloads approach 100 GB before other traffic; this is not a hard visitor limit. Lookahead can make a short visit exceed the minimum projected bytes. |
| 5. Prefix loader | **Mostly accepted** | Replace general interval tracking and adaptive prefetch with a committed prefix, two bounded processing slots and three-chunk lookahead. Two requests still arrive out of order; ordered commitment is required. Date ties are handled by the complete count index, but remain a regression case. Keep contract-level overlapping-read cancellation and a single loader generation/disposal check; a hidden selector does not eliminate async lifecycle risks or the supplied source-switch fixture. |
| 6. Preallocation | **Accepted as a measured trial choice** | Replace initial growth/block machinery with fixed selected-count buffers. Nominal data is 57,338,240 CPU bytes plus 35,836,400 GPU bytes. Three.js uploads full arrays on creation; update ranges do not avoid that first upload. Include it in startup, memory and recovery costs; make no partial-graphics-memory claim. |
| 7. Defer worker | **Accepted, technical premise corrected** | Main-thread bounded preparation first; add a worker only for a measured bottleneck. Async digest does not prove decoding/preparation is below a frame. A local probe with the unchanged webpack flags emitted a separate worker and ran it at both root and `/Orrery3D/`; those flags alone do not force a config change. A real later worker still needs its own integration verification. |
| 8. Epoch alignment | **Accepted** | Prepare/commit synchronously at the cloud epoch. If a worker is later added, stamp batches and rephase only a stale-epoch range before commitment. Keep the phase correctness regression. |
| 9. One class | **Accepted** | Normalize whole mode to one internal descriptor spanning the selected count. Keep the original index/source identity, exact empty/range semantics and equivalent verification. No second module/cache framework. |
| 10. Pinned URLs | **Accepted with retention caveat** | Use `data/delivery-v1-<index-hash>/`. Identity-safe URLs prevent mixing but do not retain old assets after deployment. Define retention/rollback and missing-old-chunk behavior before publication. |
| 11. Smaller matrix | **Partly accepted** | Start performance exploration with one paired run on native and one throttled profile. Reuse the existing browser suite rather than create a large performance matrix. Retain all contract/lifecycle/error vectors, current three-browser CI, focused renderer regressions, repeated primary measurements before a favorable conclusion, and the standing independent integration-review requirement. ## Answers to the review's open questions

1. **Archive location:** propose an immutable release in `orrery-data`. None exists for this derivative; no publication is performed or assumed. The trial uses the retained local bundle and shared fixtures, with the same provisioner designed to accept a real immutable URL later. A runtime-host/publication decision remains separate.
2. **Chunk size:** retain the existing 1 MiB pin first. It supports a small complete initial population and bounded hash/parse buffers. Measure before trying 2–4 MiB; a changed derivative has a new exact index pin.
3. **Production default:** remain on historical 100k during the trial. Passing the budgets supports a rollout recommendation, not an automatic switch. Full dated rollout also needs public data availability and actual Pages delivery/recovery checks.
